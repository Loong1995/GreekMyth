本文档是客户端阶段唯一任务入口。开始任何工作前完整阅读本文档。
本阶段产出的所有文档按第 8 节的文档体系规则存放和索引。

## 0. 项目背景（压缩上下文，长期有效）

产品：全球发行的希腊神话题材 2D 卡牌对战手游。SLG 式战法组合深度，无大地图，主打个人竞技 Rank 赛。神 / 人 / 海 / 冥界四阵营。

商业目标：以「立绘 + 战法组合深度 + 战斗爽感」建立区分度，让玩家将情感投射到英雄卡牌，驱动抽卡与养成。客户端表现层是这一目标的直接兑现者。

总体架构：服务器权威。battle/ 下的 Python core 已完成 Phase 1 验收：

simulate(battle_setup, seed) -> battle_report

纯函数产出权威战报 + 反演事件流。

客户端只播放、不结算。事件流契约（docs/schema/battle_events.md + battle_events.schema.json）已冻结，是前后端唯一共同依赖，客户端无权修改，只能提出加法式演进的申请（记录到 decisions 并询问）。

战斗形态：每队最多 3 名武将，1 准备回合 + 最多 8 正常回合，系列连战最多 7 局。

事件流带 seq / t / group_id / parent_seq 树状分组，支持战法级折叠播放与逐效果展开播放两种粒度（详见 docs/dev/playback_model.md，Phase 1 已产出并确认）。

团队现实：个人开发 + AI 辅助（Cursor + Unity MCP），极小美术预算。代码与文档必须极度重视：可读、可测、可小步演进、上下文可低成本重建。

## 0.1 美术与表现策略（本阶段最高设计纲领，所有实现决策服从它）

主流观感的来源排序：打击反馈（顿帧/震屏/闪白）> 演出节奏（镜头/暗场/飘字）> 特效质感 > 角色动画精度 > 立绘动态化。前三项只花工程时间，是 AI 辅助最擅长的部分。

因此：

- 战斗单位 = 卡牌本体（带阵营边框的立绘卡），不做骨骼动画小人。这个阶段只做battle中已配置的英雄的，立绘先去网上随便下一些对应英雄占位图直接做，下到一个指定目录，以后我直接换立绘和头像。
- 效果说明：攻击 = 卡牌突进/挥砍位移 + 命中特效。不同的攻击和技能，产生伤害的话都用一套卡牌移动+攻击的动作，但是若该伤害是由英雄自带战法(非主动/追击)机制触发的，额外在被结算者头上显示伤害来源者头像。不同控制/负面效果视觉特效不一样，施加到卡牌上，到期后移除该效果。一些特殊效果允许单独配置特效，例如宙斯的雷霆是施加后全队动态雷电环绕。要允许支持后续各种效果对应特效的扩展。
- 对标 Marvel Snap / Slay the Spire 的验证结论。
- 立绘"活"感靠 shader 与网格形变伪造：
  - 视差伪 3D 卡面（立绘 2~3 层 parallax）
  - 呼吸缩放
  - foil 流光
  - 稀有度边框粒子
- 一次开发全角色复用，是本路线质感天花板，值得投入最多打磨时间。
- 技能演出 = 通用模板 + 特效差分：
  - 4~6 套 Timeline 演出模板
  - 单体突进斩
  - 全体弹幕
  - 增益光环
  - 单挑事件 cut-in 
  - 击杀伤害产生时，cut-in+震撼特效
- 单个技能只换特效贴图、颜色、参数。
- 大招 cut-in = 立绘 + 斜切黑边 + 速度线 + 震屏，零新增美术。
- 打击感三件套（hit stop、震屏、受击闪白）自研，几百行代码，全局复用。

## 3. 播放器硬性工程要求



## 3.1 表现与逻辑绝对分离（最高优先级）

客户端不做任何战斗数值计算。

以下内容一律取自事件 payload 与状态镜像：

- 飘字数字
- 兵力条终值
- 状态层数

发现事件流数据不足以支撑某表现时，禁止客户端自行推算，记录到 decisions.md 申请契约加法式演进并询问。

任意时刻中断/跳过播放，状态镜像必须与「播完到该 seq」完全一致。

镜像更新与表现触发原子绑定，禁止表现协程里顺手改镜像。

播放器对未知事件类型必须优雅忽略并告警日志（契约加法式演进的向前兼容），但对已知类型的 payload 缺字段必须显式报错。

## 3.2 演出健壮性

任何单个演出（Timeline/DOTween/粒子）异常或超时（超模板预算 2 倍）不得卡死播放队列：

- 超时强制收敛到该事件的镜像终态并继续
- 同时输出错误日志

倍速与跳过在任意演出中途触发都必须安全收敛。

应用暂停/切后台恢复后播放状态一致（移动端现实）。

## 3.3 可排查性

headless 播放日志（B1 落盘物）是客户端侧的 replay_dump 对应物：

- 给任意战报即可离线核对「客户端理解的战斗过程」
- 与服务端 replay_dump 输出人工可比对

表现层错误日志必须带 battle_id + seq 上下文，客诉可定位到具体事件。

- enableFrontend 开关
- 播放粒度
- 倍速

该入口从 B1 起始终保持可运行，每个 Step 验收都以它为演示载体。

## 5. 性能与质量指标

目标机型：

- 中端 Android（参考 Snapdragon 7 系）稳定 60fps
- 战斗峰值（全屏大招 + 满场状态图标 + 飘字）不低于 45fps
- 编辑器内 Profiler 无单帧 >16ms 的 GC 尖峰
- 对象池覆盖后战斗循环内 0 GC alloc 为目标
- 偏差写入报告解释

战斗场景包体增量（不含立绘）≤ 50MB。

单局播放启动（战报加载到第一个事件开演）≤ 1s。

## 6. 表现设计硬性要求

打击感三件套接入所有 damage 表现。

强度按 hint 分档：

- 普攻
- 技能
- 暴击
- 大招

分档参数集中在一个 ScriptableObject 配置，便于整体调味。

暴击必须有明确的差异化表达：

- 飘字样式
- 音效触发点
- 闪白增强

四阵营视觉识别：

- 边框
- 特效主色调
- cut-in 底纹

规范写入：

docs/client/faction_style.md

所有玩家可见文本走统一文案表（为未来多语言留位），禁止硬编码字符串。
