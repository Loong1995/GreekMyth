## 0. 项目背景（压缩上下文，长期有效）

- 产品：全球发行的希腊神话题材 2D 卡牌对战手游。SLG 式战法组合深度（对标三战/三谋/率土
  的战法体系），无大地图，主打个人竞技 Rank 赛。神 / 人 / 海 / 冥界四阵营。
- 商业目标：以「立绘 + 战法组合深度 + 战斗爽感」建立区分度，让玩家将情感投射到英雄卡牌，
  驱动抽卡与养成。一切设计服务于此。
- 总体架构：**服务器权威**。服务端完成全部战斗结算，生成权威战报 + 反演事件流数据包，
  客户端（Unity 播放器）仅按事件流播放演出，不做任何结算。**事件流即播放协议，
  battlecore 的底层机制必须以支撑客户端多粒度反演播放为基准来设计**（详见第 3 节）。
- 战斗规模：每队最多 3 名武将，每武将默认 10000 兵（不设硬上限，未来特殊场景可能有
  超 10000 兵的 NPC）。回合制自动战斗。
- 现状：
  - `battlecore/` 下有初版 Python core：**战斗模拟已跑通、伤害数值已标定平衡**，且附有
    较丰富的设计文档；但其中「连携 / 单挑 / 犹豫 / 连击」等新机制只有描述、从未实现，
    且架构未考虑确定性、事件流输出、运维排查和长期演进。分析时须核对文档与代码的
    实际 match 程度，以代码实际行为为准。
  - `reference/golden_replays/` 下有少量旧 golden 战报样例。**数量少、参考价值有限**，
    主要用于参考输出格式与数值量级，不作为逐字节回归基准（详见 4.3）。
- 团队现实：个人开发 + AI 辅助。代码与文档必须极度重视：可读、可测、可小步演进、
  上下文可低成本重建。

**只读红线：`battlecore/` 与 `reference/` 全部为只读参考，禁止修改其中任何文件。**

## 3. 事件流契约要求（本项目最重要的单一契约）

Schema 一经确认即冻结，此后只允许**加法式演进**（新增事件类型、新增可选字段），
禁止修改或删除已有字段语义。契约文件是前后端唯一共同依赖。

**必须支持客户端反演播放的多种粒度需求**：有时客户端需要按「单个战法」级别整体播放，
有时需要按「战法内每个单次效果 + 连锁伤害效果」依次播放；在草案中再论证是否有其他
播放需求（如跳过至结果、逐回合快进、单挑独立演出等）。**以此为基准设计 battlecore 的
底层机制和事件流**——这是本次重构的第一目的。

### 3.1 数据包整体结构

- `battle_report`（顶层包）= **一个完整系列**（1~7 局连战，见 5.1）：
  `schema_version`（语义化版本）、`battle_id`、`rng_seed`、`core_version`、
  双方阵容与初始属性快照、`games[]`（每局含局序号、局内 `events[]`、局结果）或等价的
  带局号扁平事件流（草案中论证选型）、`result` 系列总摘要（最终胜负、总局数、剩余兵力、
  关键统计——用于列表页展示，客户端无需播完事件即可显示结果）。
- 每个事件必须含：`seq`（系列内全局单调递增序号）、`t`（逻辑时间：局号 + 回合号 +
  回合内相位 + 相位内序号）、`type`、`payload`。
- **播放分组结构**：事件需支持树状归属——一次战法释放产生的所有子效果（多段伤害、
  连锁、状态施加等）通过 `group_id` / `parent_seq`（或草案论证的等价机制）挂到该次
  释放之下，客户端据此选择折叠（战法级播放）或展开（逐效果播放）。
- **逻辑与表现分离**：事件只携带结算事实（谁、对谁、多少、什么状态）。可附带可选
  `hint` 字段供演出参考（如暴击、大招级别），但客户端演出不得影响结算。事件流必须
  自洽完备——只看事件流即可完整还原战斗，无需重新计算。

### 3.2 事件类型（最小集，可在草案中论证增删）

battle_start / game_start（每局开始，含本局初始兵力快照）/ round_start / phase_start /
action_start（某武将行动）/ normal_attack / skill_trigger（区分准备、释放、被打断、
受犹豫延迟）/ damage / heal / status_apply / status_refresh / status_tick /
status_remove / attr_change（属性修改，如单挑败者四维-10）/ troops_change /
hero_defeated / duel_challenge / duel_result（单挑叫阵与胜负）/ game_end / battle_end。
草案中每个事件类型必须给出：字段表、触发语义、一个 JSON 实例。

### 3.3 格式与传输

- 开发期使用 JSON（可读、可 diff、便于 golden 测试）；Schema 设计须保证未来可无损
  映射到 Protobuf/FlatBuffers（字段编号预留、避免动态键名），文档中写明映射约定，
  本阶段不实现二进制编码。
- 给出单局与 7 局满打系列的战报体积估算，并说明超长战斗（回合上限）的截断策略。

## 4. 新 BattleCore 硬性工程要求

### 4.1 确定性（最高优先级）

- 同一 `(rng_seed, 双方阵容, core_version)` 输入，任何机器任何时间产出**逐字节相同**
  的事件流。
- 单一 RNG 流，种子外部注入；禁止使用系统时间、字典无序遍历、set 迭代顺序等不确定源；
  所有需要遍历的集合必须有显式确定的排序规则（写入机制文档）。
- 数值计算优先使用整数/定点；如必须用浮点，在文档中说明并论证跨平台一致性。
- 这是回放、客诉排查、反作弊、断线重连的共同地基，不得为便利妥协。

### 4.2 性能

- 目标：单进程纯模拟（关闭事件序列化）≥ 100 局/秒（3v3 满编、普通回合数、以单局计，
  系列按局数折算；基准机器为开发机）；开启事件流输出时给出实测数据。
- 批量模拟入口按正式功能实现（运营期调平衡的日常工具，不是临时脚本）。

### 4.3 数值忠实迁移与回归验证（三层）

1. **公式单测**（主要防线）：从旧 core 提取全部伤害/治疗/属性公式，逐条写成带期望值
   的单元测试。
2. **统计等价验证**：旧 golden 数量少、参考价值有限（主要参考输出格式与数值量级），
   不要求逐字节对齐。改为：**仅用旧 core 已实现机制**组阵容，新旧 core 各跑 ≥1000 个
   种子，胜率与均伤偏差在文档声明的容差内，逐项解释偏差来源。新机制（单挑/连携/
   犹豫/连击等）不参与此对比。**禁止为对齐统计结果而擅自修改已标定的伤害公式**；
   若怀疑旧公式有 bug，记录到 decisions.md 并询问，不得自行"修正"。
3. **新 golden 冻结**（此后的真正基准）：验收通过后用新 core 生成一批新 golden 战报
   入库（`battle/tests/golden/`），覆盖各机制类型阵容。CI 逻辑：任何 PR 若改变 golden
   输出，必须显式更新 golden 文件并在 commit message 中说明原因。

### 4.4 机制架构

- 战法系统采用**事件驱动 + 优先级**架构：战法通过订阅触发时机（如「行动开始时」
  「受到伤害时」「普攻命中后」）挂接效果；同一时机多个战法的结算顺序必须有全局确定的
  优先级规则（规则写入机制文档）。同一武将多个战法同时机触发时，以装配顺序为准。
  架构要为数百个战法的组合可扩展性负责——这是「战法组合深度」核心卖点的地基。
- 状态作为一等公民建模：来源、层数、持续时间、互斥/覆盖规则统一管理。
- core 对外只暴露纯函数式入口：`simulate(battle_setup, seed) -> battle_report`。
  不持有跨场次状态。`battle_setup` 须支持指定武将初始兵力（支撑超 10000 兵 NPC 与
  测试场景）。
- 扩展方式以代码层为主（新增战法=新增类/注册），不做配置文件级别扩展，除非必要。

## 5. 游戏规则硬性要求

### 5.1 战斗结构与系列连战

- 单队最多 3 名武将（可少于 3），设主将 1 名。
- 每局 = 1 个准备回合 + 最多 8 个正常回合。
- **仅主将阵亡判定该局失败**。若一局打满仍未分胜负则为平局：所有存活武将**伤兵不恢复、
  以残血兵力进入下一局，除残血外一切战时状态（增益/减益/控制/延迟中的行动）均清空
  重置**，直到决出胜负，一个系列最多 7 局，仍无胜负判系列平局。
- 一个 `battle_report` = 一个完整系列（见 3.1）。
- 每武将 1 个自带战法 + 2 个可配置战法格。战法结算顺序：由触发机制决定；同时机则以
  装配顺序为准。
- 任何结算与状态变化，凡判断需要客户端播放表达的，都必须事件化输出。

### 5.2 效果原语（战法由原语组合而成）

1. **物理伤害**：受武力属性影响，系数可配置 = 系数 1 的标定伤害 × 系数倍率。
2. **魔法伤害**：受谋略属性影响，系数可配置，同上。
3. **治疗**：将结算目标的伤兵转为兵力，主要受智力属性影响（属性字段以 Step A
   术语统一表为准）。
4. **施加状态 / 移除状态**：见 5.3。
5. **属性修改**：临时或整场修改武将属性（如单挑败者四维 -10）。
- **普攻** = 系数 1.0 的物理伤害内置战法，默认人人携带，伤害沿用旧 core 已标定结果。
- **暴击** = 伤害/治疗结算流程中的独立乘区，按几率提高倍率；是否暴击必须在对应
  damage/heal 事件中表达给客户端。石化的受伤 +10% 所在乘区位置：Step A 提案。

### 5.3 状态清单

默认规则：**除非特殊说明，负面状态不可刷新、不可叠加**；所有状态的生效与结束
（含被清理）都必须事件化给客户端。

| 状态 | 类别 | 叠加 | 效果语义 |
|---|---|---|---|
| 中毒 / 燃烧 | 负面 DoT | 否 | 持续 N 回合，每回合按谋略结算一次掉血 tick |
| 缄默 | 负面控制 | 否 | 禁释放主动战法，N 回合；若目标有准备中战法则**额外产生打断**（缄默+打断两个事件，两种特效） |
| 缴械 | 负面控制 | 否 | 禁普攻，N 回合；因此无法触发追击 |
| 冥锁 | 负面控制 | 否 | 禁主动 + 普攻，N 回合 |
| 石化 | 负面控制 | 否 | 禁主动 + 普攻，受到伤害 +10%，N 回合 |
| 犹豫 | 特殊 | **可叠加** | 行动时主动/普攻有几率延后生效，延后回合数 = 叠加层数；事件表达为「xx 释放战法 xx，受犹豫影响延后 X 回合生效」 |
| 正面增益 | 正面 | 按各自定义 | 属性提升、连击率提升、暴击率提升等临时状态 |
| 特殊状态 | 特殊 | 按各自定义 | 准备回合施放的状态不分正负，一律按特殊状态管理 |

犹豫的边界情况（延迟期间施法者阵亡/被缄默或冥锁/目标阵亡/延迟跨越局边界——战时状态
不跨局，延迟中的行动随局清空）：Step A 提案 + 交互矩阵逐格测试（Step B3）。

### 5.4 高级系统

1. **追击**：一类被动战法的触发时机，定义为「己方普攻命中后」触发的附加效果。
   缴械/冥锁/石化禁普攻即无追击。本阶段至少实现一个追击型示例战法验证该时机。
2. **连击**：武将有连击率（可被战法/状态提升），连击率 100% 则普攻两次；每次普攻
   独立触发追击判定。设计若干能提升连击率的主动或被动示例战法。
3. **单挑**：每局开局（所有战法执行前、准备回合最前）立即判定：若两队均有武力 > 90
   的武将，双方武力最高者触发单挑——高武力方向低武力方叫阵，低武力方按武力差有几率
   拒绝；接受则决出胜负，**负者四维立即 -10**。叫阵、拒绝/接受、胜负均事件化给客户端。
   胜负判定公式与拒绝几率公式：根据武力差执行随机，武力差10时是必定结果。
4. **连携**：主将自带战法为神谕类型时，主将在准备回合释放神谕后，两名副将的自带战法
   若为主动，各有 k 几率触发连携立即释放一次（准备类战法无需准备直接释放）。
   k 的取值/来源：可固定配置。
5. 未明事项默认参考三战、三谋的通行做法，重大分歧记录 decisions.md 或询问。

### 5.5 死亡与退出战斗（必须确认鲁棒）

1. 兵力为 0 的武将立即退出战斗。
2. 退出战斗的武将：不再行动、不再成为正常目标；**其施加给所有其他武将的全部状态
   立即删除并清理干净**（清理本身事件化）。其订阅的所有触发时机同步注销。
3. 配套专项测试：死亡瞬间有 DoT 未结算、死亡者有延迟中的犹豫行动、死亡者是连携
   来源等边界场景。

## 6. 示例武将、战法文档与运维支撑

### 6.1 示例武将与战法

- `battlecore/config/skill_files.py`：已有若干示例英雄的自带战法描述与部分实现，
  另有几个**只有描述未实现**——全部实现，并对位到合适英雄的自带战法槽位。
- `battlecore/config/basic_test_damage_skills.py`：样板式期望系数测试技能，作参考；
  另造若干覆盖各类型（主动爆发 / 被动触发 / 持续状态 / 全局类 / 神谕 / 追击 / 连击）
  的自带战法测试武将配合测试，以验证战法架构表达力。
- 逐英雄逐机制测试，含边缘用例。

### 6.2 战法三段式文档（`docs/skills/<skill_id>.md`）

1. **玩家版**：希腊神话风格、精简传神（≤60 字），卡面文案；
2. **开发者·机制版**：触发时机、目标选择、数值公式、优先级、与其他机制交互、
   边界情况（目标已死、被打断等）；
3. **开发者·程序版**：订阅的事件信号、产出的事件类型、涉及的类/函数、优先级常量、
   状态 ID。

### 6.3 运维与排查

- 每份战报自带 `rng_seed` + `core_version`，任何客诉可一键本地复现整个系列。
- `replay_dump` 工具：输入战报 JSON，输出人类可读的逐局逐回合战斗文本日志（运营与
  策划排查用，不依赖客户端）。支持**全量**与 **brief** 两档：brief 只输出客户端反演
  所需事件，冗余判定与内部更新不打印。
- core 内部错误不得静默吞掉：结算异常必须使战斗失败并输出完整上下文，禁止产出半截战报。

## 7. 文档体系与上下文管理规则（长期有效，写入仓库根 README 与 .cursorrules）

目录约定：

    docs/
      prompts/      # 每阶段任务书（本文件即 phase1_battlecore.md），只读存档
      schema/       # 契约文档 + JSON Schema，冻结后加法式演进
      dev/          # v0 分析、播放模型、决策记录、changelog
      mechanics/    # 机制文档：index.md + 每机制一个小文件
      skills/       # 每战法一个三段式文档
    battle/         # 新 core 实现
      tests/        # 单测 + golden 回归
      benchmarks/   # 性能基准
    battlecore/     # 旧 core，只读，禁止修改
    reference/      # 旧 golden 样例，只读，禁止修改

文档编写规则（为 Cursor 有限上下文优化）：

- `docs/mechanics/index.md` 是机制主文档：写清整体机制流（一个系列从入口到结束的
  完整时序），每项机制 2-4 句精要 + 链接独立机制文件。只读 index.md 即可建立全局图景，
  只加载相关机制文件即可处理局部问题。
- 每个文档文件 ≤300 行；超出则拆分并在 index 登记。
- 每完成一个模块同步更新文档，**文档与代码不同步视为任务未完成**。
- 仓库根维护 `.cursorrules`：项目一句话背景、当前阶段与当前 Step、契约文件路径、
  目录约定、编码红线（确定性规则、golden 更新规则、battlecore//reference/ 只读）。
  每个 Step 结束时更新「当前 Step」。
- 每个工作会话结束时，将改动摘要追加到 `docs/dev/changelog.md`（日期 + 3-5 行）。
