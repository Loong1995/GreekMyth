## 二、静态立绘 PNG 规格（先做，收益最大）

一张图**同时**服务四处，所以它是整个方案的地基：卡面立绘、单人 cut-in 巨幅、
决斗半屏卡、头像标（`UnitView.ShowPortraitMark`）。

| 项 | 要求 |
|---|---|
| 路径 | `Assets/Resources/ClientBattle/Portraits/`（**放 `Assets/Resources/Portraits/` 不生效**） |
| 文件名 | roster 英文 `template_id`，见 §六清单（`heracles` 不是 `heracules`） |
| 格式 | PNG，**透明背景**（主体去背） |
| 尺寸 | 高 **≥1080 px**；构图**竖版**，建议 1024×1680（与卡框 `antique_frame.png` 同比） |
| 导入设置 | Inspector → Texture Type = **Sprite (2D and UI)**（留 Default 会 `Resources.Load<Sprite>` 读不到，仍显色块） |
| 内容 | 半身/胸像（bust），面向偏正前，留出下颌到胸口的完整轮廓 |

运行时一律**等比 contain** 塞进槽位（`UnitView.FitSpriteToSlot` /
`CutInService.NewPortrait`），不拉伸、不裁切，所以极端扁图会在槽位里留大边。

## 三、cut-in 构图安全区（按代码实测换算，16:9）

数值出处 `VFX/CutInService.cs`。以屏幕高度为 1 单位。

### 单人 cut-in（`SoloRoutine`）
触发：满势能满档 / 单条伤害 >3000 / 行动窗第 5 次追击（阈值见 `Events/CutInPlanner.cs`）。

- 立绘槽位：**宽 55% 屏宽 × 高 75% 屏高**（`halfW*1.1` × `halfH*1.5`，contain）
- 立绘中心停在**屏幕横向 64% 处**（偏右；`portTo.x = halfW*0.28`）
- 大字标题在**左下**（`textTo` ≈ 屏宽 33% / 中线下 9%）
- 背景是阵营色斜带（倾斜 12°）+ 55% 黑幕

> **构图红线**：主体偏右、**左下留白给标题**。角色视线/武器朝向建议朝左
> （朝向标题与画面内侧），朝右会把观众视线带出画外。

### 单挑 cut-in（`DuelStage`）
触发：单挑事件（仅第 1 局开局，全场一次），`clash_cutins` 1~3 轮。
分幕见 [duel.md §5b](../mechanics/duel.md)。

立绘被**从卡框里揪出来**飞进中央虚空展示屏，左右各一名：

- 立绘槽位：**宽 35% 屏宽 × 高 55% 屏高**（`DuelSlotWidth/Height` × 半宽半高，contain）
- 槽位中心：横向距屏心 **±21% 屏宽**（`DuelSlotX`），纵向近中线（+2% 屏高）
- 背景：虚空展示屏（95% 屏宽 × 66% 屏高的近黑底 + 冷光边）+ 78% 黑幕
- 中央有单挑图标（15% 屏高见方），**两侧立绘不要越过屏心**，否则会压住图标
- **不再有名字条**（旧半屏卡版本的下压名字已取消），下部可以放细节

> **构图红线**：单挑用法**主体居中**、单人 cut-in 用法**主体偏右**。同一张立绘
> 要同时满足两种用法——所以主体本身居中、靠**画布留白**制造偏移，
> 不要把角色画到画布边缘。

### 单挑屏华饰（可选，传了更精致）

屏体的辉光/放射/浮尘/黑边/背光/冲击环全部**程序化生成**，不传图也不难看；
传同名真图即自动顶替（`DuelStageChrome`）：

| key | 内容 | 尺寸建议 |
|---|---|---|
| `UI/duel_icon` | 中央单挑图标（交叉双剑/月桂之类），透明背景 | 512² |
| `UI/duel_rays` | **整张**放射光芒（白色，透明背景，中心对称）。传了就用单张顶替 N 个渲染器，更省更好看 | 1024² |
| `UI/duel_corner` | **只画左上角**一枚纹饰，其余三角由代码镜像复用 | 256² |
| `UI/duel_screen_bg` | 屏底纹理（暗色石纹/星空/神殿浮雕皆可），会被压暗并叠阵营辉光 | 2048×1024 |

> 这四张是**性价比最高的一笔**：一次投入，全部单挑复用，且不随武将数量增长。

## 四、单挑动作 flipbook 规格

### 4.1 两段动作、逐帧图、不是视频

每名武将交付**两段**序列：

| clip | 内容 | 用在 |
|---|---|---|
| `strike` | 出手：起手 → 挥击 → 收势 | 本轮攻方；**末轮双方同时播** |
| `react` | 挨打：格挡/踉跄/后仰 | 本轮守方 |

命名 `{template_id}_{clip}_{NN}.png`，`NN` 从 **`00` 连号**（`00 01 02 …`），
**断号即停**，上限 64 帧。放
`Assets/Resources/ClientBattle/DuelAction/`。

> 为什么逐帧图不用视频：单挑要**两人同屏同时播**（移动端双路视频解码有风险），
> 且 flipbook 按 `ctx.Scaled` 算帧下标，**天然吃 0.5×/2×/4× 倍速**——
> `VideoPlayer.playbackSpeed` 与播放时间轴是两套时钟，变速必然脱拍。

### 4.2 帧数与时长

单段播放窗口 = `DuelActionSeconds`（默认 1.0 s 常速，末轮 ×1.35），
再乘 `DurationMul`（默认 2）与玩家调速。**帧数由你定，代码按窗口把整段均匀铺满**
——帧多就播得细，帧少就播得糙，**不会**播不完或播过头。

- 推荐 **12~18 帧**（≈12~15 fps 的手绘节奏，1 s 正好一遍）；
- **不必**无缝循环：一段只播一遍，播完自动回静态立绘；
- **首帧建议贴近静态立绘**：进入动作时是从静态立绘切过去的，差太远会跳一下。

### 4.3 画面

| 项 | 要求 |
|---|---|
| 分辨率 | 高 **≥1080 px**；与静态立绘**同画布、同构图、同比例**（代码按**首帧**算 contain 缩放，各帧画布必须一致，否则会跳大小） |
| 透明通道 | **需要**（PNG 带 alpha）。主体叠在展示屏底上 |
| 导入设置 | 每张 Texture Type = **Sprite (2D and UI)** |
| 动作幅度 | 主体**不要移出画布**。位移感由 `DuelStage` 的交错飞行负责，帧内再大位移会打架 |
| 镜头 | 不要推拉摇移 |

### 4.4 体积预算

单武将两段合计 **≤3 MB**（导入后）。本项目做过一次贴图内存专项治理
（723→258 MB），不能吃回去。超预算就**减帧数**，不要降分辨率——
帧少只是糙一点，分辨率低了在 55% 屏高的槽位上直接糊。

> 优先只做**会参战的武将**：单挑参赛资格是**有效武力 > 有效智力**，
> 智力型武将永远不会进单挑，给他们做动作是纯浪费。

## 五、制作流程（AI 管线）

1. **先出静态立绘**：统一 prompt（`greek mythology, 2D card game portrait,
   bust, painterly`）+ 阵营配色（见 [faction_style.md](faction_style.md)），
   32 张全量出齐、去背、按 §二 命名上传。**这一步单独就能看到最大提升。**
2. **图生视频（i2v）出动作**：把上一步的 PNG 作为**首帧**喂给视频模型，
   分别生成 `strike` / `react` 两小段。详见 §5b。
3. **抠像 + 抽帧**：见 §5c。
4. **改名连号**：`{template_id}_{strike|react}_00.png` 起连号，丢进
   `Assets/Resources/ClientBattle/DuelAction/`，全选设 Sprite (2D and UI)。
5. **验收**：对照 §九 清单。

### 5b. 怎么让 AI 生成能用的 flipbook

**唯一正确的路线是「图生视频（i2v）→ 抽帧」，不是「让 AI 直接画 N 张」。**
逐张生成必然身份漂移——第 3 帧的披风纹样和第 7 帧对不上，连起来是在闪，
不是在动。i2v 由单张首帧驱动，帧间一致性是模型自己保证的。

**关键约束：首帧＝该武将的静态立绘原图**（不要重新生成一张"差不多的"）。
动作段是从静态立绘切过去的，首帧不一致就会跳。

**提示词写法**（以阿喀琉斯 `strike` 为例）。本文提示词一律用**中文**书写，
主流视频模型（可灵 / 即梦 / 海螺 / Vidu 等）中文理解好于英文直译：

```
[首帧图：achilles.png]
这名战士举起长枪向前突刺，披风与头发被动作带起。
镜头锁死，不推不拉不摇。
人物始终居中，双脚站定，不要移出画面。
背景保持纯绿色不变。
```

四条必写、少一条就废：

| 必写 | 为什么 |
|---|---|
| 镜头锁死，不推不拉不摇 | 模型默认爱推镜头。镜头一动，抠出来的主体会在槽位里漂——而槽位里的位移是 `DuelStage` 的交错飞行负责的，两者会打架 |
| 人物始终居中，不要移出画面 | 主体出画等于中途缺半个人 |
| 背景保持纯绿色不变 | 为抠像铺路（见 §5c） |
| 动作写**一次完整的动作**，别写"战斗中" | 「战斗中」会生成一段没有起止的乱动，抽帧后首尾对不上 |

`react` 段同理，动作换成
「这名战士被击中后踉跄后退，举盾格挡，头部后仰」。

**时长**：让模型出 2~3 s 即可，抽帧时只取中间最连贯的一段。
**不要**追求长片，帧数上限 64、实际只用 12~18 帧。

**批量做法**：32 个武将 × 2 段 = 64 段。先只做 §六 第一批 8 人的 16 段，
在游戏里看过一次再决定要不要铺开——观感不达标的话，早发现比返工 64 段便宜。

### 5c. 抠像与抽帧（这一步最容易翻车）

视频模型**不吐 alpha**，所以必须自己抠。绿幕是成本最低的路子：

1. 生成时就要求纯绿背景（§5b）；
2. 抠像用 ffmpeg 一条命令直接出带 alpha 的 PNG 序列：

```bash
ffmpeg -i achilles_strike.mp4 -vf "chromakey=0x00FF00:0.30:0.05,fps=15" \
       achilles_strike_%02d.png
```

`0.30` 是相似度阈值（绿边没除干净就调大，主体被啃掉就调小），
`fps=15` 顺带完成抽帧（2 s × 15 ≈ 30 帧，再手工删到 12~18 帧）。

三个坑：

- **绿边**：头发/半透明布料边缘会留一圈绿。抠完扫一眼，严重的用
  `despill` 或在 PS 里做一次边缘收缩。放到屏上时立绘有背光垫着，
  轻微绿边看不出来，但发丝上的整片绿会很脏。
- **各帧画布必须一致**：ffmpeg 出的序列天然一致，**不要**再逐帧裁剪。
  代码按**首帧**算 contain 缩放，画布不一致会逐帧跳大小。
- **连号从 `00` 起、中间不能断**：`%02d` 从 01 开始，记得整体改名或改用
  `-start_number 0`。断号即停——`_00 _01 _03` 只会加载到 `_01`。

### 5d. 单挑展示屏背景图（`UI/duel_screen_bg`）

单挑屏的底目前是程序化合成的纯色 + 渐变，**够用但不够史诗**。换一张 AI 底图
是这块屏性价比最高的一次升级：只加一个文件、零代码，`DuelStageChrome`
检测到同名真图就自动顶替（占位三级回退）。

| 项 | 要求 |
|---|---|
| 路径 | `Assets/Resources/ClientBattle/UI/duel_screen_bg.png` |
| 分辨率 | **2048×1024**（2:1）。屏宽 `DuelScreenWidth`≈1.9 半宽、高 ≈1.32 半高，接近 2:1 |
| 透明通道 | **不需要**（它是底，整块铺满） |
| 导入设置 | Texture Type = **Sprite (2D and UI)** |
| 体积 | ≤1.5 MB（导入后） |

**构图硬约束**（不满足就白做）：

- **左右两侧各留一个"人位"**：立绘落在 ±0.42 半宽处、占约 55% 屏高。
  这两块必须是**低对比度的暗区**，主体压上去才立得住。所有细节、
  高光、纹样一律往**中轴**和**四角**放。
- **中央要能承受一个图标**：屏心会浮现单挑图标并放冲击环，中轴留出一块
  相对干净、偏暗的区域。
- **整体压暗**：屏上还会叠阵营辉光、放射光芒、浮尘、边框呼吸。底图越花，
  这些动态元素越糊。**底图是"场"，不是"画"。**
- 不要在图里画任何人物、武器、文字——都会和立绘/图标打架。

**生成提示词**（中文，配 Midjourney / 即梦 / 文心一格等均可）：

```
古希腊神话竞技场的虚空对决场景，横向宽幅构图。
画面中央是一道下沉的青铜圆形斗场，四周环绕破碎的大理石列柱与断裂的台阶，
背景是翻涌的暗色云海与远处若隐若现的奥林匹斯山轮廓。
空中悬浮着细碎的火星与飞灰。
整体**大幅压暗**，只有中轴保留一束自上而下的神性冷光。
**画面左右两侧保持深色、空旷、无细节**（留给人物）。
不要出现任何人物、动物、武器、文字、水印。
史诗感，电影级布光，体积光，厚涂油画质感，高细节，2:1 超宽画幅。
```

反向提示词（negative）：

```
人物, 角色, 脸, 武器, 文字, 水印, 标志, 拼贴边框, 高饱和, 明亮平光, 杂乱构图
```

**验收**：把图丢进去跑一场带单挑的战报，看两件事——
① 左右立绘是否"浮"在底上（浮就是底太亮/太花，回去压暗）；
② 中央图标与冲击环是否还看得清（看不清就是中轴太花）。

> 同理可选的另外三张（不传则程序化生成，**不影响可玩性**）：
> `UI/duel_icon`（中央单挑图标，方形 512，需 alpha）、
> `UI/duel_rays`（整张放射光芒，方形 1024，需 alpha，省 N 个渲染器）、
> `UI/duel_corner`（**左上角**纹饰，方形 256，需 alpha；其余三角由代码旋转复用）。

## 七、代码侧状态（工程，非美术）

单挑 flipbook 链路**已实现**，上传即生效：

- 加载与回退：`VFX/DuelStage.cs::Fighter.LoadFrames`（连号扫描，断号即停，
  零帧则退单帧静态立绘）；
- 帧推进：按 `ctx.Scaled` 后的进度取帧下标，**天然吃倍速**；
- 硬停止：`CutInService.CancelAll` 销毁挂点并 `DuelStage.Restore()` 还原卡面立绘
  （R-1.2：停止后场上不得残留推进中的动画或空卡框）。

未做、也**不打算**做：`VideoPlayer` 路线（alpha 封装、移动端单路硬解、
`Prepare()` 100~500 ms 黑帧、变速脱拍——四个问题 flipbook 全无）。

尚可优化（非阻塞）：帧序列目前在单挑发生时才 `Resources.Load`。单挑仅
第 1 局开局一次且前面有号角+台词铺垫，实测不卡；若日后前移，接
`PlaybackWorldBuilder.PrewarmFromReport` 扫 `duel_challenge` 预载即可。

## 八、为什么不做「卡内攻击视频」

- 攻击三拍总长约 0.54 s，且正处在突进/残影/弹道/裂地/命中/震屏/飘字**最拥挤**
  的半秒，卡牌本身只占屏幕一小块且后倾 45°——卡内微动画基本看不见。
- 视频**不吃** `ctx.Scaled`：移动端硬解对非 1.0 倍速支持差，会与三拍脱拍。
- 同样的素材预算放到 cut-in：镜头独占、时间拉长、事件稀有，收益高一个量级。

若日后仍想让卡内动起来，用**序列帧 flipbook** 而非视频（原生 alpha、可按
`ctx.Scaled` 缩放、可池化、可硬停止，直接接现有 `SpriteRenderer`）——
单挑动作（§四）走的就是这条路，可直接复用其加载与回退写法。
